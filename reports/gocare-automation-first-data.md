# GoCare centralized test data and fixture design

The case ID is the lookup key for the per-case data profile in [traceability](gocare-automation-first-traceability.csv). Use the verified TestRail Test Data and Expected Result fields first, then apply the profile below. Keep data ownership, tenant, authorization, and provenance in the [synthetic record registry](gocare-synthetic-record-registry.md). The implementation phase can use typed scenario data through the existing data provider. Existing search samples need a registry check before reuse.

The [draft control datasets](../testdata/gocare-ui-draft-datasets.json) hold exact case-keyed values and approved request boundaries. The company and medical catalog groups run each dataset row in a fresh draft, preserving the exact filter while checking and unchecking Show only Active. Keep every search or mutation blocked for those groups. Positive personal identifiers continue to come only from the approved fixture manifest.

## Generation and lifecycle

- Reuse `utils/randomDataGenerator.ts` and `utils/dataProvider.ts` conventions where compatible. Use case ID, run key, and worker ID as a reproducible seed. Generate alphabetic name suffixes for letters-only fields, date-only values in the UAT timezone, and integer candidates within verified local field limits.
- Check every fixture identifier against the approved tenant and allowed lookup scope before creating data. Record the exact seed or fixture reference and ownership. Use a new candidate after conflict only where the operation is authorized. Keep the approved deferred employee candidate pinned to GIN 97101.
- Existing inputs include `testdata/logindata.json`, `testdata/logindata.csv`, `testdata/employee-search.json`, `testdata/create-emp-data.json` and `testdata/gocare-synthetic-fixtures.json`. Consult the repository fixture and registry before extracting an example. Keep secrets, recipient allowlists, storage state and protected values out of case text, traces and rendered artifacts.
- Track each fixture as planned, owner-approved, provisioned, verified, expired or cleanup-pending. Keep read-only shell and no-submit fixtures disposable through browser context isolation. Coordinate any server cleanup separately with the UAT owner.

The [fixture requirements](gocare-synthetic-test-data-requirements.md) and [UAT owner provisioning plan](gocare-testrail-master-progress.md) provide the per-dependency roles, cases, and approval conditions.
